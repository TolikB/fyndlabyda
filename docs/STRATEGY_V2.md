# Стратегія v2: чому paper-серії втрачали гроші і що змінено

Дата: 06.10.2026. Гілка: `codex/paper-strategy-v2` (від `ce8fd8f`, розгорнутого релізу
`paper-series-sim201-20261003`).

## 1. Що показали перші 2,7 дні candidate/baseline

Дані: 61 закрита угода, 2905 підтверджених можливостей, `funding_snapshots` і
`funding_history` з VM (03.10 15:45 – 06.10 08:20 UTC).

| Показник | Значення |
| --- | --- |
| Повне коло угод (вхід + вихід, обидві ноги) | **0,334%** від суми однієї ноги: комісії 0,205%, slippage 0,129% |
| Отриманий funding за угоду | ~0,145% |
| Реалізовано від очікуваного (`ставка на вході × тримання`) | **23%** |
| Кореляція поточної ставки з фактичним edge за наступні 24 год | **0,00** |
| Кореляція фактичного edge за попередні 24 год | 0,36 |
| Кореляція `persistence_score` / `funding_stability_score` | ~0,5 |
| Угод, закритих рівно після мінімальних 8 год | 40 з 61 |

Висновки:

1. **Прогноз доходу хибний.** Сканер вважає, що поточна ставка funding триматиметься
   24 год (`SCANNER_EXPECTED_HOLDING_HOURS`). Але відібрані можливості — це сплески,
   які швидко повертаються до середнього, тож поточна ставка не прогнозує наступну добу.
2. **Ранжування обирає сплески.** У `score_opportunity` APR множиться на 100·0,35, тож
   net_apr 13,9 дає ~486 балів, а ліквідність — максимум 20.
3. **Вихід надто ранній і дорогий.** Лічильник `low_edge_streak` набирається ще під час
   мінімального тримання, тому `funding_edge_decay` спрацьовує одразу після 8 год.
   Правило закриває і малий *позитивний* edge, хоча тримати його безкоштовно, а
   закриття коштує ~0,17%.
4. **Пари з різними інтервалами (1h/8h) найгірші.**
5. **Оцінка slippage під реальний розмір — правильна** (0,121% проти фактичних
   0,130%). Удвічі занижена лише 1-одинична оцінка сканера в таблиці `opportunities`.
6. 11 «закрив і одразу відкрив той самий актив» — це не баг, а розворот пари після
   зміни знака funding (інший `opportunity_key`).

Застереження: вибірка мала (2,7 дні, 72 пари), режим ринку — альткоїни зі
сплесками funding. Цифри орієнтовні; саме тому зміни перевіряються як нові
paper-серії, а не вмикаються в чинних.

## 2. Що змінено в коді

Усі зміни opt-in через три необов'язкові блоки серії в YAML. Серія без них поводиться
як раніше, і її відбиток (`config_hash`) не змінюється: блок, якого немає, не потрапляє
в identity. Тест `test_series_without_new_blocks_keep_their_recorded_hash` фіксує
хеші живих `candidate-sim201-20261003` і `baseline-sim201-20261003`.

### `selection` — відбір входів

| Поле | Що робить |
| --- | --- |
| `min_stability_score`, `min_persistence_score` | мінімум відповідних оцінок сканера |
| `max_interval_ratio` | відсікає пари, де довший інтервал funding більш ніж у N разів довший за коротший (1h/8h = 8) |
| `reentry_cooldown_hours` | не входити в актив N год після закриття (відновлюється з БД після рестарту) |
| `forecast` | прогноз edge = `current_weight × поточний + (1 − current_weight) × середній фактичний за lookback_hours`; вхід лише якщо `прогноз × horizon_hours / 8 − повне коло витрат ≥ min_expected_net` (витрати — з оцінки під реальний розмір) |
| `rank_by: expected_net` | порядок входів за прогнозованим чистим результатом, а не за APR |

### `holding` — вихід

`exit_confirmation_minutes`: edge має бути нижче `exit.exit_funding_rate_8h` увесь цей
час (час, а не кількість циклів). Разом із від'ємним `exit_funding_rate_8h` і довшим
`min_hold_hours` позиція виходить лише тоді, коли тримати її справді дорожче.

### `execution` — пасивні ордери

`maker_entry` / `maker_exit`: одна нога (з ширшим спредом) стоїть пасивним ордером на
своїй стороні книги, друга хеджується тейкером у момент виконання. Модель
консервативна:

* ордер виконаний лише тоді, коли пізніша книга **пройшла крізь** його ціну (bid
  вище за наш ask, ask нижче за наш bid); дотик не рахується, бо позиція в черзі
  невідома;
* виконання перевіряється до рішення про скасування, бо реальний fill стається між
  циклами;
* незахеджована нога не записується: якщо друга книга недоступна, ордер перевіряється
  в наступному циклі;
* вихід після `maker_timeout_seconds` без виконання закривається тейкером; вхід або
  скасовується, або (з `entry_fallback_taker`) іде тейкером;
* різниця ціни виконання з mid на момент fill записується як slippage (adverse
  selection);
* відкладені ордери існують лише в пам'яті: рестарт їх скидає, нічого не записавши.

`SIMULATOR_VERSION` лишився 2.0.1: для серій без `execution` правила виконання не
змінились, а серії з `execution` мають цей блок у своєму відбитку.

### `funding-arbitrage replay-rules`

Програє правила серій на записаних даних (`opportunities` + `funding_snapshots` +
`funding_history`) без перекриття угод; угоди, відкриті на кінець періоду, рахуються
до кінця з повними витратами.

```bash
docker compose exec app funding-arbitrage replay-rules --series-file config/paper_series.v2.yaml --days 7
```

Спрощення: фіксовані витрати 0,334% на коло (`--cost`), пасивне виконання — знижка
0,06% (`--maker-saving`), без ліміту капіталу, сигнали є лише там, де стек брав книги.
Інструмент ранжує набори правил, а не прогнозує дохід.

## 3. Експеримент: `config/paper_series.v2.yaml`

Окремий стек (`docker-compose.paper-v2.yml`, проєкт `funding_arbitrage_paper_v2`,
порт 8001, своя БД), щоб живі серії зберегли свої слоти книг, бюджет історії та код.
Чотири серії по 1000 USDT, 50 USDT на позицію, до 8 позицій; кожна додає одну зміну:

| Серія | Зміна |
| --- | --- |
| `control` | правила live-candidate (еталон у тому самому стеку) |
| `patient` | + мін. тримання 24 год, вихід при edge < −0,05%/8h протягом 60 хв, cooldown 8 год |
| `quality` | + `persistence ≥ 90`, інтервали ≤ 4×, прогноз (w=0,1, 24 год, горизонт 48 год, ≥ +0,1% після витрат), ранжування за прогнозом |
| `quality-maker` | + пасивна нога на вході та виході (180 с) |

Програвання на записаних 2,7 днях (до запуску; більшість угод ще відкриті, тож це
лише перевірка інструмента): `control` −0,235% на угоду (49 угод), `patient` +0,050%
(12), `quality` −0,079% (8), `quality-maker` −0,047% (9).

## 4. Як оцінювати

* Не раніше ніж через 7 днів і ≥ 50 закритих угод на серію: середній результат на угоду
  після витрат > 0, частка виграшних, результат без найбільшого активу.
* `GET /analytics/compare?a=quality&b=control`, `/analytics/series/<label>/attribution`.
* `replay-rules` на даних v2-стека — для нових порогів до запуску нової серії.
* Переможця переносити в основний `paper_series.yaml` лише новою серією з новим `label`.
